# 09 · 任务管理器

> v2.3 新增的教学载体：**用 VS Code 原生 Task API 做「投影」而不是自己解析
> `tasks.json`**——`fetchTasks()` 取回任务后按 `source + scope` 过滤，执行只调
> `executeTask(原生对象)`。教学价值在「识别哪些事必须交还宿主」这条边界：
> 变量替换、provider 解析、`dependsOn` 编排全部由引擎完成，扩展零复制。

## 核心机制

### 1. 只加载工作区 tasks.json：`source + scope` 过滤

VS Code 对 tasks.json 任务（含 `shell`/`process`/`npm` 等 contributed type）的
source label 硬编码为 `'Workspace'`；用户级 tasks.json 与 `.code-workspace` 级
任务共享该 source 但 **scope 退化为 `TaskScope.Workspace`（非文件夹对象）**。
因此一个条件即可精确锁定：

```ts
task.source === 'Workspace' && typeof task.scope === 'object' // WorkspaceFolder
```

这是对 VS Code 内部约定（非公开 API 语义）的依赖，已用宿主集成测试实证
（`src/test/extension.test.ts` 的 Task Explorer suite，断言仓库自带
`npm: compile` 可被发现）；若未来 VS Code 变更约定，该测试会先行报警。

### 2. 执行红线：只运行 `fetchTasks()` 返回的对象

`executeTask(task)` 发现任务带内部 `_id` 时按 `(workspaceFolder, id)` 交回主线程
**重新解析**，`dependsOn` / `dependsOrder` / 循环检测 / 失败短路全部由引擎完成。
自建 `new vscode.Task(...)` 没有内部 `_id`，走 DTO 重建路径会**丢 `dependsOn`**——
所以命令参数归一化（`resolveEntryArg`）后仍坚持使用原 Task 对象，
树节点的 `TreeItem.command.arguments` 也直接传原始 Task。

### 3. 三组根节点与运行态

- 最近运行 / 收藏 / 工作区任务三个 group 节点持有**固定实例**（只替换 children），
  刷新后展开状态不丢；空组也显示「暂无」占位；
- 运行态在 `getTreeItem` 时实时查询 `status.isRunning(key)`（扫描
  `tasks.taskExecutions`，不缓存布尔值）→ 最近运行/收藏/工作区任务三处显示天然一致；
- `onDidStartTask` / `onDidEndTask` 只触发 100ms 去抖的 `fire()`（不重新
  `fetchTasks`）；`fetchTasks` 仅由 watcher（300ms 去抖）/ 工作区变化 / 信任授予 /
  手动刷新触发（单飞合并）。

### 3b. 图标三级判定

任务条目图标按「运行态 > 分组 > 类型」判定（`taskIcon`）：运行中一律
`sync~spin`；否则 build → `tools`、test → `beaker`；再否则按 `definition.type`
取 `shell → terminal` / `process → gear` / `npm → package`；未知 contributed
类型回落 `terminal`。

**坑**：真实宿主中对象形式分组（`"group": {"kind": "build", "isDefault": true}`）
经 API 返回的 `TaskGroup` **不是** `vscode.TaskGroup.Build` 单例——分组比较必须用
`task.group.id`（字符串）而非对象身份；E2E（真实 fetchTasks）实证过这一差异，
单测桩因复用同一常量对象暴露不出来。

**坑（v2.4）**：清单里的命令图标只能是真实存在的 codicon——`$(star-filled)`
并不存在（codicon 集是 `star` / `star-empty` / `star-full` / `star-half`），
写错时按钮**静默不显示**，门禁不校验 codicon 名。已对照
`node_modules/@vscode/codicons/dist/codicon.css` 核对本功能用到的全部图标名。

### 3c. label 树形分组（v2.5 配置化，继承 vscode-taskexplorer）

`buildTaskTree` 按**设置**把平铺任务拆为虚拟文件夹树，设置项与开源项目一一对应
（`extStarter.` 前缀 + `task` 开头，设置变更触发全树重建走单飞 refresh）：

| 设置（默认）                      | 对应开源项          | 语义                                             |
| --------------------------------- | ------------------- | ------------------------------------------------ |
| `taskGroupWithSeparator`（true）  | groupWithSeparator  | 分组开关；关闭 = 全部平铺叶子                    |
| `taskGroupSeparator`（`-`）       | groupSeparator      | 分隔符                                           |
| `taskGroupMaxLevel`（1，1-5）     | groupMaxLevel       | 拆层上限；超出部分保留在叶子里（短名拼回剩余段） |
| `taskGroupStripTaskLabel`（true） | groupStripTaskLabel | 叶子显示剥掉分组路径前缀的短名（无剩余回退全名） |

叶子节点的 `entry`（任务身份/运行/收藏匹配）恒用完整 label，仅 `displayLabel`
影响显示名——tooltip 首行即完整名。边界约定不变：任务名与虚拟文件夹同名 → 并入
该文件夹；空段忽略；虚拟文件夹 `id = taskFolder:<uri>:<前缀路径>`。

**有意不继承的开源行为**（设计红线）：特殊夹恒显（开源的 showLastTasks 可关掉
整个夹，我们 G7 要求三组恒显空态占位）、单击即运行（开源默认 Open 打开定义文件）、
不加载用户级任务（开源有 User Tasks 夹）。

另：视图清单支持 `visibility: "collapsed"`（VS Code 1.48+），v2.4 起
「任务管理器」排视图组首位、其余视图默认折叠（用户手动展开后由编辑器记忆）。
最近运行展示条数 `taskNumLastTasks` 可配（存 20 展 N），**运行中的任务置顶**
（对齐开源 pushToTopOfSpecialFolder；我们的记录语义不变：仅本扩展运行成功才入列）。

### 4. 持久化与容错

- 存储结构 `{ version: 1, favorites: TaskRef[], recent: RecentTaskRef[] }`，
  key 为 `scopeUri + '\u0000' + source + '\u0000' + name`（多根同名任务不串扰）；
- 读取校验：整体非法 → 重置为空 + 输出通道告警；单条非法 → 丢弃该条；
  `recent` 读取去重保留最新、上限 20（展示层再截 10），`favorites` 不设上限；
- 写失败（`memento.update` 拒绝）不阻断 UI：内存状态继续生效并告警；
- 匹配不到当前任务列表的 ref（任务改名/文件夹移除）**隐藏但保留**，
  任务恢复后自动出现。

### 5. 定位到 label 行：轻量 JSONC 扫描

`locateTaskLabel(text, name)` 只认双引号字符串 / 行注释 / 块注释 / `\` 转义：
只有「字符串后随冒号」的 token 被当作键（命令文本里的 `label` 字样不会误命中），
值按 JSON 转义解码后与任务名全等比较，重复 label 取第一个，BOM / 尾逗号 /
截断文件一律容忍且**绝不抛异常**。未命中返回 `undefined`，命令降级为
「打开文件顶部 + 提示」。零新增依赖（不引入 jsonc-parser）。

## 扩展实操

### A. 让视图支持另一类任务源（以「用户级任务」为例，仅演示思路）

1. `taskSource.ts` 放宽 `isWorkspaceFileTask`（或新增判断函数）并给 entry 增加
   来源标记；
2. 树 provider 的 `buildTasksChildren` 按来源分组渲染；
3. 单测更新 `taskSource.spec.ts` 的过滤矩阵（正/负用例都要加）。

注意：放宽过滤前先想清楚「最近运行 / 收藏的 key 是否仍稳定」——跨机器的
用户级任务 scopeUri 可能不同，key 设计需随之调整。

### B. 在 tooltip 里展示依赖（P2 方向，需新增 jsonc-parser）

`Task.definition` 不含 `dependsOn`（API 边界），要展示依赖必须只读解析
tasks.json（设计方案 §4.4 的 P2 增量）。运行仍走原生引擎，解析结果仅用于展示。

## 常见坑

- **`executeTask` 收到自建 Task**：依赖不执行、报「找不到任务」——检查归一化
  路径是否误用了 `new vscode.Task` 或重建了 execution；
- **运行态不刷新**：确认走的是 `TaskStatusTracker.onDidChange`（只 fire）而不是
  在事件回调里重新 `fetchTasks`（会闪树 + 丢展开状态）；
- **多根同名任务互相终止/误收藏**：key 必须包含 `folder.uri`（`taskKey` 已处理，
  自定义 key 时容易漏）；
- **清单门禁红**：`VIEW` 的 `*ViewId` / `COMMAND` 与 `package.json` 必须双向闭合，
  `view/item/context` 的 `when` 必须含 `view ==`（见开发指南 07）。
